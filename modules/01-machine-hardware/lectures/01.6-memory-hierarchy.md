## Story

Your CPU doesn't see RAM. It sees registers (1 cycle), then L1 (4c, 32KB, 64B line), then L2 (12c, 256KB), L3 (40c, 8MB shared), then RAM (80ns, 4K pages), then SSD (50µs+). The line is **64B** — one cache miss brings 64B, even if you only wanted 4B.

**Why sequential wins:** `for (i=0; i<N; i+=1) sum+=a[i]` touches every byte of a line — next access hits. `i+=16` (64B apart) touches 1 int per line, wastes 60B, but does 1/16th the work — *per element* it's slower. See `04-cache-stride.c`: time/element is worse for stride 16 after normalizing.

**TLB:** Virtual `0x7fff1234` → physical via page table (4 levels on x64). TLB caches `VPN→PFN` for 4K pages. Random 4K jumps → TLB miss → 4 memory reads (page walk). `huge pages 2M` reduces misses 512×.

**False sharing:** Two threads, same 64B line, different variables `a` and `b` 8B apart — they ping-pong the line `M→I→M`. Fix `alignas(64) int a; alignas(64) int b;` — separate lines.

## Code — Try Now

```c
// 04-cache-stride.c — see bench
#define N (16*1024*1024)
static int a[N];
for (int i=0;i<N;i++) a[i]=i;
volatile long s=0;
for (int it=0;it<4;it++) for (int i=0;i<N;i+=1) s+=a[i]; // sequential
for (int it=0;it<4;it++) for (int i=0;i<N;i+=16) s+=a[i]; // 64B stride
```

Run: `gcc -O2 04-cache-stride.c -o stride.exe && ./stride.exe` — compare `time/element`.
